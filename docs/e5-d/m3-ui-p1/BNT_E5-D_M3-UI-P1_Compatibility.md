# M3-UI-P1 — Compatibility and persistence

This candidate adds **creation request version 3**, not a new career-save format. Career schemas 1–6, envelope-v1/v2, presentation sidecar-v1/v2, immutable recruitment pack pins, commentary settings and active-team selection retain their existing validators and formats. Version-1/2 creation requests retain their historical schema-2 output.

A version-3 creation prepares the unchanged package grant in isolated memory. It then invokes the existing economy migration, payroll migration, championship foundation migration, controller enablement, E3 enablement and E5 catalog enablement commands. Every intermediate result passes the existing domain/store validators. No existing career is passed through this sequence automatically.

The completed schema-6 candidate is encoded and validated using the existing complete-backup/restore preparation. Its career slot is reserved before staged restoration, but becomes playable only after the existing atomic IndexedDB head activation. A retained stage can be validated and resumed. An interruption before activation exposes no playable partial career; an interruption after activation is recovered as the same committed identity. Identical retries use existing duplicate protections; conflicting package/presentation retries reject. A version-3 request cannot replace an existing older-schema career.

Initialization installs the existing payroll context without running a championship cycle, charging wages, applying recovery, crediting rewards or changing starting Gold. Existing starting-driver contracts retain their existing grandfathered wage/duration rules. The wizard discloses these obligations using the same native contract constructors.

Contextual action cards use `actionQuote` and `actionCommand`. Confirmation retains the prepared command's expected career/maintenance revisions and quoted terms. A stale commit fails; the UI refreshes and requires confirmation again. Navigation does not publish a transaction. There is no second save authority, pricing implementation or service scheduler.

The existing Options Save/Load controls retain career-only JSON, complete backups, imports, staged restore, recovery and deletion. Main-navigation Save/Load is removed; its internal route opens Options. Manual Save Game verifies accepted durable career boundaries. It does not save in-memory race progress or Strategy Signs.

The accepted P1 policy remains: ordinary playback and Signs run in the buffered Worker/in-memory attempt; closing an unfinished race restarts the same saved seeded starting boundary. Official publication, Run/Legacy choices, final settlement and archives retain their existing authority. The presentation patch relocates diagnostic controls without removing their functions.

Existing saves are not normalized, downgraded, silently migrated or stripped of sidecar data. Old careers retain explicit compatibility/recovery controls under Options → Save & Load → Recovery and older careers. Prior accepted/candidate HTML files are preserved; the new artifact has a separate filename. Browser-local storage remains origin/file-context dependent; external complete backups remain advisable. Windows direct-file acceptance is an owner test, separate from managed Chromium HTTP checks.

|---|---|---|---|

The v3 request uses the existing request fields (`id`, `slotId`, `profileId`, `careerId`, `ownerName`, `careerName`, `packageId`, `emblem`, `primary`, `secondary`, Boolean `recruitIdentities`) with `version: 3`. Unknown fields and unsupported v4 reject. This request is not a replacement save envelope or a new mechanical-state schema.
