# M2-C Revision 2 — Final Design Reconciliation Register

**Authority:** Owner approved M2-C-01..36 and pre-approved remaining M2-C design decisions; this document makes the Codex-preflight reconciliation explicit. These are **design choices**, not assertions that native engine support has been implemented or independently verified. Codex's preflight was read-only on `main` at `105bce8a2a8f639b56c703cd75c56ce212471021`, 293 tests passing.

## R2-01 — Corrected fixed initial market tiers
The original category rows summed **9 Budget / 9 Standard / 5 Premium**, conflicting with approved overall **9 / 10 / 4**. Retain overall 9/10/4 and change **equipment from 3/2/1 to 3/3/0**. Final rows: drivers 2/2/1; beasts 2/3/1; chariots 1/1/1; specialists 1/1/1; equipment 3/3/0. This removes the formerly described guarantee of a Premium equipment offer. Category totals remain 5/6/3/3/6 = 23. This is an explicit adjustment under advance design approval, not a source fact.

## R2-02 — Valuation-health H, repairs and refurbishment
Version **`valuation-health-v1`** is an **economic valuation projection**, not an engine performance formula. All H inputs are finite and in [0,100]; invalid/missing values reject, never clamp malformed source. H driver = native `condition`; H beast = native `condition`; H chariot = management `integrity`. The chariot choice values physical repairability, **not** native race performance; native `condition` and `wear` remain distinct. For beast and chariot starting/resale valuation, use the original unmodified **base rating mean** (exclude training and engineering) and persisted quality. `C(H) = 0.70 + 0.30 × H / 100`.

Chariot repair increases **management integrity only**, maximum 100, with no implicit native condition/wear change. Chariot refurbishment decreases native `wear` only, minimum 0, with no implicit integrity/condition change. Driver recovery reduces management fatigue only; beast care reduces native beast fatigue, already bridged by the M2-B assembly adapter. Injury treatment changes management injury only. These mappings must be implemented in schema-v3 paths without changing M2-B or racing engine calculations. No direct native `integrity` field may be introduced.

**Valuation formula:** Current beast/chariot reference valuation = `referenceTierPrice × permanentQuality × C(currentH)`; resale = `min(originalAcquisitionBasis, floor(0.50 × currentReferenceValuation))`. Original acquisition basis for starter beast/chariot = `round_to_nearest_5(referenceTierPrice × Q × C(originalH))`; for purchased assets it is actual paid acquisition price. Persist original base rating, Q, original H and acquisition basis separately; engineering/training never improves resale valuation. Use full decimal precision until specified rounding. The same 0.70..1.00 condition factor applies to new driver/beast/chariot offer prices, but **not specialist or equipment offers**; specialists are condition-neutral in the initial market. Any older text that implies condition-discounted specialists is superseded.

## R2-03 — Schema-v3 injury and eligibility
Schema v2 preserves exact M2-B strings `Healthy`, `Minor`, `Moderate`, `Severe`, `Dead` and its existing eligibility. Schema v3 uses management `Healthy=0`, `Minor=1`, `Major=2`, `Critical=3` and **does not silently convert legacy nonhealthy strings**. Eligible v2→v3 migration accepts verified `Healthy` only; any other legacy injury value returns a typed `UNSUPPORTED_LEGACY_INJURY` blocker, preserving source. New schema-v3 injury treatment decrements one severity level; Healthy is no-effect. `Minor` may race subject to native checks, `Major`/`Critical` may not. Preserve assignments even if current injury or condition makes an RU temporarily ineligible; flag invalid RU on preview/race entry, never silently disassemble or rewrite historical assignment. Schema-v2 validation/preview remains unchanged. No `Dead`→`Critical` coercion.

## R2-04 — Existing starting equipment and resale references
Each M2-B package has **two owned equipment records** with stable IDs and reciprocal installation references. They must migrate in place, not be fabricated. Neutral equipment (`mass:0`, `combat:0`) retains no bonus or slot mechanic. Label strings are not a pricing tier. Assign **Budget tier** to every starter equipment record solely for valuation metadata, with immutable acquisition basis **100 G per item** (Budget reference price); no charge or purchase transaction. Original item label remains unchanged. Starting equipment resale is `floor(0.40 × 100) = 40 G` per item. Acquired equipment resale is 40% of **actual acquisition price**, floored. For any installed equipment sale, reject `EQUIPMENT_INSTALLED` until a separate **explicit `equipment.detach`** command succeeds; it must atomically clear both ends of existing installation references and must not add a new slot/bonus mechanic. Chariot resale requires RU disassembly/unassignment and **all installed equipment explicitly detached first**; never silently bundle, delete or orphan equipment. Detached items remain owned. If the source's reciprocal links cannot support a safe detach command, block that command and report before implementation.

## R2-05 — Initial offer generation (version `market-generator-v1`)
Deterministic category-tier counts are fixed by R2-01. Use an isolated seeded PRNG derived from persisted career ID and generator version, using canonical UTF-8 seed material `BNT|M2-C|market-generator-v1|<careerId>` and a specified stable algorithm recorded in the source and fixtures; **do not use timestamps or racing RNG**. Generate exactly 23 offers in stable category order `driver`, `beast`, `chariot`, `specialist`, `equipment`, then tier order Budget/Standard/Premium, then ordinal; ID = `m2c-offer-<category>-<tier>-<ordinal>` within a career (uniqueness is scoped by career ID). All randomized values must be produced from the isolated stream and persisted. Deterministic generator algorithm and seed-byte-to-integer mapping must be fixed in code with golden vectors **before** acceptance; no silent algorithm swap. This explicit remaining verification requirement is not a license to use platform-dependent randomness.

For each generated **native rating**, use the inclusive integer rating ranges: Budget 30–49, Standard 50–69, Premium 70–89. Independently draw each allowed native rating from the tier range; no unapproved hidden modifiers. Driver 5 ratings; beast 6; chariot 5. Specialists have **no invented native ratings**: tier and role are management metadata. Specialist roles are exactly one each: `Beast Handler` Budget, `Mechanic` Standard, `Physician` Premium. Equipment remains neutral `{mass:0,combat:0}` with labels `Basic equipment <ordinal>` for Budget and `Standard equipment <ordinal>` for Standard; no premium equipment. Driver/beast/chariot native `condition` generated as inclusive integer 70–100, native driver `strain=0`, beast `fatigue=0`, chariot `wear=0`, chariot `weight=180`, `capacity=400`; chariot management `integrity` generated as inclusive integer 70–100. New management fatigue=0, injury=Healthy, XP=0. New specialists start management Healthy, and are condition-neutral for price. Market-quality modifier: draw an integer `q` uniformly from 85..115 and set `Q=q/100` (inclusive, exact decimal); condition factor from R2-02 for driver/beast/chariot; none for specialists/equipment. Wage-quality modifier for newly offered personnel: draw integer `w` uniformly 90..110, set `w/100`, persist. All source-verified fields and species/other required identity metadata must be supplied through approved schema-v3 factories; use generic draft beast species if required. If an offer cannot be represented with native validation, fail the **entire** market generation, not a single offer. Do not use the above rating bands to reclassify tier: generated tier is an explicit market property. Market values and order are immutable after persistence.

## R2-06 — Fractional ratings and rounding
Use continuous cost bands `0 ≤ r < 60`, `60 ≤ r < 75`, `75 ≤ r < 90`, `90 ≤ r < 100`; cost for each requested +1 uses its **current pre-increment** rating. Reject increments that would exceed 100; do not round native rating to choose a band. Use **decimal half-up** for positive nearest 5 G and nearest 1 G, and **ceiling** only where explicitly specified (chariot repair base proportional to actual integrity restored; final discounted training XP). Floor resale proceeds. All values must be finite, bounds checked, and economic calculations must avoid binary-floating rounding artifacts at ties. For chariot repair: `ceil(15 × actualIntegrityRestored / 10)` before additive percentage discounts, then nearest Gold half-up, minimum 1. Apply discounts only to eligible specialist/facility effects, additive capped at 25%, never compound. Costs are computed and validated before atomic debit.

## R2-07 — Protected migration receipt and revision accounting
Migration is **maintenance-only**: do not consume a gameplay revision, invent a gameplay transaction, or append a gameplay receipt that would break the M2-B invariant `gameplayRevision == activeGameplayReceiptCount`. Use a **distinct, versioned protected migration-maintenance record variant** inside the retained protected-history outer schema v1, preserving all existing v0/v1 entries byte-for-byte. The record is keyed to career ID, source/target schema, source fingerprint and migration rules version and is committed atomically with career v3, market, contracts and valuations. Increment maintenance revision exactly once on successful migration; gameplay revision unchanged. Exact confirmation retry must return the retained migration acknowledgment if present; protected migration identity without full acknowledgment returns `ALREADY_COMMITTED` with null receipt; conflicting ID/payload rejects. The new record **does not count toward gameplay receipt ledger** but must count toward the protected-identity limit (2000). Maintain M2-B limits (1000 active gameplay receipts, 2000 protected identities, 8 MiB import). No history pruning. Validate all before single storage write, including whether the migration maintenance variant can be represented without breaking old protected-history validators. If outer v1 cannot support a strictly additive variant, **stop and request separate owner approval for protected-history schema increment**; never mutate old receipts or relax v1 validators. M2-B v1 command semantics remain intact. The M2-C command v2 envelope remains the approved basis for economic gameplay transactions; the migration maintenance record is a separate typed maintenance action and must not masquerade as gameplay command v2.

## R2-08 — Grandfathered wages and source preservation
Grandfathered starter driver wage-quality modifier is exactly `1.00`, stored once. Starter Standard contracts have 8 cycles remaining, no recruitment/signing charge and no wage accrual until M2-D.
